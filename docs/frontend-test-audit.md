## 发现并修正的问题

1. 原场地表单的部分无效输入测试直接派发 `submit`，绕过浏览器原生校验。真实 Chromium 中，容量为 `0` 时请求虽被拦住，但页面没有显示测试断言的本地错误。预约人数超容量存在同类问题。测试改为点击提交按钮，先观察失败，再让两种表单统一运行页面校验；浏览器复查均显示明确错误且未发送 POST。
2. 原预约列表测试仅保证创建后的新记录不会被晚到的旧列表覆盖，没有检查旧列表里的其他记录。新测试先复现遗漏，再合并列表与已确认的本地写入，并以取消后的状态覆盖旧列表中的有效状态。
3. 原创建预约响应校验未核对 `booked_by` 和 `purpose`。新增不匹配响应测试先失败，再补齐字段比较，避免把错误对象当作创建成功。
4. 预约提交期间只禁用按钮，输入仍可修改，而成功回调会清空草稿。补充待提交状态的输入断言后，将表单输入一并禁用；浏览器复查证实等待响应时不可编辑。
5. 场地和预约列表原先缺少无效成功响应的直接测试。新增非数组、非法容量以及取消状态与时间不一致的样例，均被 API 客户端拒绝。
6. 再次检查发现：预约列表请求发出后如果本页创建了预约，迟到的列表会把页面内**所有**旧记录置于服务器返回值之上，掩盖其他客户端对旧记录的取消。先新增复现用例，确认原实现失败；然后仅保护该请求之后本页成功创建或取消的记录，其他记录采用服务器返回值。

## 实际结果与边界

修正前的基线为 98 项自动测试通过。本次新增 10 项，最终 `npm test` 为 **10 个测试文件、108 项通过**（包含模拟 API 的 19 项）；`npm run build` 的 TypeScript 检查和生产构建通过，`git diff --check` 通过。

真实 Chromium 点击场地容量 `0` 与预约人数超容量时，页面均显示本地错误且没有 POST；有效预约提交过程中输入被禁用，收到符合契约的成功响应后显示编号。此前创建场地、预约与取消、停用场地和 20 组响应式布局的模拟 API 浏览器检查记录见[场地创建检查记录](frontend-create-venue-check.md)。

本轮再次运行真实 Chromium + 本地模拟 API：空表单阻止请求；预约成功后清空草稿；重叠时段返回冲突并保留草稿；相邻时段成功；列表状态筛选、取消二次确认、刷新后保留取消状态、取消后重订均通过；模拟断网显示错误，恢复后刷新成功；浏览器无运行错误。新发现的列表竞态由回归测试覆盖。模拟 API 测试已确认包含在 `npm test` 中。

剩余验收边界：尚未对真实 Java API、PostgreSQL 或 Docker Compose 三服务执行联调；浏览器检查是本地执行记录，尚未纳入仓库自动测试。完整系统正确性须在真实服务可用时按[验收清单](acceptance.md)继续验证。
