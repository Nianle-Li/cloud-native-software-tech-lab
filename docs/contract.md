## 1. 范围与架构

本阶段交付一个可从源码重新构建的单体业务系统，包含三个独立运行的 Compose 服务：

```text
浏览器 ──HTTP──> frontend (Nginx + 静态页面)
                     │ /api/* 反向代理，保留原路径
                     ▼
                  api (Spring Boot)
                     │ JDBC，database:5432
                     ▼
               database (PostgreSQL + named volume)
```

- 前端只通过 HTTP JSON API 访问后端，不直连数据库；后端负责所有业务校验和持久化。
- Compose 服务名固定为 `frontend`、`api`、`database`。仅 `frontend` 必须映射宿主机端口；数据库不映射宿主机端口。
- 项目根目录放 `compose.yaml`，便于直接运行 `docker compose up --build -d`。Compose 默认网络可满足服务名解析，不为本实验预先增加微服务、消息队列、缓存或认证系统。
- Lab 1 不设计登录与权限。`booked_by` 是预约人或组织的展示字段，不代表已验证身份；取消接口目前不限制操作者。后续 Lab 如加入认证，需发布新的接口契约。

## 2. 数据与业务语义

### 2.1 数据模型

数据库表名采用复数形式 `venues`、`reservations`；主键为数据库生成的 `BIGINT`。数据库列和 JSON 字段使用 `snake_case`。`Venue 1:N Reservation`，`reservations.venue_id` 为非空外键。业务日期和时段按 `Asia/Shanghai` 的本地日期/时间解释；创建与取消时间作为带时区时间戳保存。

| 实体 | 必需字段 | 数据库约束/含义 |
|---|---|---|
| `venues` | `id`, `name`, `location`, `capacity`, `open_time`, `close_time`, `status` | `name`/`location` 非空；`capacity > 0`；`open_time < close_time`；`status ∈ {OPEN, CLOSED}` |
| `reservations` | `id`, `venue_id`, `booked_by`, `reservation_date`, `start_time`, `end_time`, `attendee_count`, `purpose`, `status`, `created_at`, `cancelled_at` | 外键有效；`attendee_count > 0`；`start_time < end_time`；`status ∈ {ACTIVE, CANCELLED}`；`created_at` 非空，`cancelled_at` 仅取消后有值 |

`open_time`/`close_time` 表示场地每日统一开放时段。本阶段预约仅限同一自然日，不支持跨午夜。预约人数 `attendee_count` 用于验证场地容量。文本长度上限：`name` 100、`location` 200、`booked_by` 100、`purpose` 500 个字符；四者均不能为空白字符串。场地列表和预约列表均返回真实数据库数据；初始化场地由 Flyway 种子数据提供，仍须支持通过 API 创建场地。

迁移文件固定在 `api/src/main/resources/db/migration/`，须与 JPA 实体映射一致。Flyway 是表结构唯一来源；JPA 使用 `ddl-auto=validate`，不得用自动建表代替迁移。新增或修改表结构只新增迁移文件，不改已执行的迁移。

### 2.2 业务规则

1. 创建场地：所有必填字段有效；`status` 省略时默认为 `OPEN`。`CLOSED` 场地可以查询，不能创建预约。
2. 创建预约：场地存在且为 `OPEN`；预约日期不得早于 `Asia/Shanghai` 当前日期，若预约当天则开始时间须晚于当前时间；`booked_by` 和 `purpose` 非空；`1 ≤ attendee_count ≤ venue.capacity`；`venue.open_time ≤ start_time < end_time ≤ venue.close_time`。
3. 冲突只在**同一场地、同一日期、`ACTIVE` 状态**之间判断。采用半开区间 `[start_time,end_time)`；当 `existing.start_time < request.end_time` 且 `existing.end_time > request.start_time` 时冲突。前一条 11:00 结束、后一条 11:00 开始允许。
4. 取消采用**逻辑取消**：保留预约记录，将状态改为 `CANCELLED` 并写入 `cancelled_at`。已取消预约不再占用时段；重复取消返回当前已取消记录，保持幂等。
5. 冲突校验必须能处理并发请求。API 在同一个数据库事务内先对对应 `venues` 行加悲观写锁，再查询冲突和插入预约；取消也先锁所属场地，再更新预约，统一加锁顺序。采用 PostgreSQL 默认 `READ COMMITTED` 隔离级别。不得只在前端检查冲突，也不得在无事务保护下执行“查询后插入”。
6. 对外不开放场地状态修改、预约改期和物理删除接口；这些不是任务书要求。后续扩展时增加接口和迁移，不改变已有字段含义。

数据库中至少设置外键、非空、正整数、时间顺序与状态约束；`ACTIVE` 的 `cancelled_at` 必须为空，`CANCELLED` 的 `cancelled_at` 必须非空。为 `reservations(venue_id, reservation_date, status, start_time, end_time)` 建立适合冲突查询的索引。Service 层仍须给出用户可理解的校验错误；数据库约束负责兜底。

### 2.3 PostgreSQL 与 JPA 映射方案

以下数据库结构已编写为 Flyway 迁移脚本。V1/V2 的原始独立验证及完整 Compose 验收记录见[验收清单](acceptance.md)；V3 的独立数据库脚本、PostgreSQL Testcontainers 升级验证和完整 Compose 复核见[实验报告](lab1-report.md#2026-10-31-功能复核与修订)。

两表均使用数据库生成的 `BIGINT GENERATED BY DEFAULT AS IDENTITY` 主键。B 使用 `Long` 和 `GenerationType.IDENTITY`，不额外创建 JPA 序列。种子数据不显式指定 ID，也不要求业务代码依赖固定的种子 ID。

以下列除 `cancelled_at` 外均为 `NOT NULL`；标为“无”的默认值表示插入时必须提供。

#### venues

| 列 | PostgreSQL 类型 | Java 类型 | 默认值与约束 |
|---|---|---|---|
| `id` | `BIGINT` identity | `Long` | 主键，数据库生成 |
| `name` | `VARCHAR(100)` | `String` | 无；不能为空白字符串 |
| `location` | `VARCHAR(200)` | `String` | 无；不能为空白字符串 |
| `capacity` | `INTEGER` | `Integer` | 无；大于 0 |
| `open_time` | `TIME WITHOUT TIME ZONE` | `LocalTime` | 无；小于 `close_time` |
| `close_time` | `TIME WITHOUT TIME ZONE` | `LocalTime` | 无 |
| `status` | `VARCHAR(10)` | 字符串枚举 | `OPEN`；仅 `OPEN`、`CLOSED` |

#### reservations

| 列 | PostgreSQL 类型 | Java 类型 | 默认值与约束 |
|---|---|---|---|
| `id` | `BIGINT` identity | `Long` | 主键，数据库生成 |
| `venue_id` | `BIGINT` | `Venue` 关联（其 ID 为 `Long`） | 无；外键引用 `venues(id)` |
| `booked_by` | `VARCHAR(100)` | `String` | 无；不能为空白字符串 |
| `reservation_date` | `DATE` | `LocalDate` | 无 |
| `start_time` | `TIME WITHOUT TIME ZONE` | `LocalTime` | 无；小于 `end_time` |
| `end_time` | `TIME WITHOUT TIME ZONE` | `LocalTime` | 无 |
| `attendee_count` | `INTEGER` | `Integer` | 无；大于 0 |
| `purpose` | `VARCHAR(500)` | `String` | 无；不能为空白字符串 |
| `status` | `VARCHAR(10)` | 字符串枚举 | `ACTIVE`；仅 `ACTIVE`、`CANCELLED` |
| `created_at` | `TIMESTAMP WITH TIME ZONE` | `OffsetDateTime` | `CURRENT_TIMESTAMP` |
| `cancelled_at` | `TIMESTAMP WITH TIME ZONE` | `OffsetDateTime` | 可空；默认 `NULL` |

接入注意事项：

- 显式指定 `@Table`、`@Column` 和 `@JoinColumn(name = "venue_id")`，与 snake_case 列名、长度及可空性一致。状态采用 `EnumType.STRING`，不使用 PostgreSQL 原生枚举或 Java 枚举序号。
- `ACTIVE` 必须同时满足 `cancelled_at IS NULL`；`CANCELLED` 必须同时满足 `cancelled_at IS NOT NULL`。状态与取消时间在同一事务中一起更新。
- 外键不配置级联删除；预约采用逻辑取消，记录保留。
- 数据库默认值仅在插入省略该列时生效。JPA 若显式插入 `NULL`，不会自动获得默认值；B 应在持久化前赋好状态和 `created_at`，或显式配置由数据库生成并读取。
- 业务日期和日内时间按 `Asia/Shanghai` 解释；带时区时间戳保存时间点，不保存原始时区名称。API 的 `HH:mm` 与 ISO 8601 格式由 B 的序列化配置保证。

### 2.4 迁移与校验职责

C 提供 `V1__create_booking_tables.sql`（建表、约束和索引）与 `V2__seed_venues.sql`（少量场地，不预置预约）；2026-10-31 新增 `V3__align_blank_text_constraints.sql`，使四个必填文本字段的数据库非空白约束与 API 的 Java 17 判定一致。已执行的 V1/V2 不回改。

种子数据包含两个开放场地（羽毛球馆 A、多功能教室 B）及一个停用场地（会议室 C），用于后续展示和停用校验。种子不指定 ID，实际 ID 以数据库查询结果为准；由 Flyway 迁移历史保证同一版本不重复执行。

迁移提供主外键、非空、文本长度与非空白、正整数、时间先后、状态及取消时间一致性约束。V3 对已有记录执行约束验证；若旧记录仅含不可见字符，须先核查并修正数据，迁移不会自动改写记录。冲突查询使用普通联合索引：

```sql
CREATE INDEX idx_reservations_conflict
    ON reservations (venue_id, reservation_date, status, start_time, end_time);
```

该索引用于辅助查询，不能独立防止时段重叠。B 的 Service 负责场地开放状态、容量、开放时段、上海时区的过去日期和当天开始时间校验，以及用户可理解的错误响应；涉及跨表或当前时间的规则不放入本阶段的行级 `CHECK`。

并发保护按第 2.2 节实现。取消时先确定所属场地，再按场地、预约的顺序加锁并重新检查状态；重复取消返回已取消记录。

## 3. HTTP API 契约

所有接口前缀为 `/api`，请求与响应正文使用 UTF-8 JSON。时间格式固定：日期 `YYYY-MM-DD`，日内时间 `HH:mm`（24 小时制，响应也不附秒）；`created_at`、`cancelled_at` 返回 ISO 8601 带时区时间戳。JSON 字段名使用 `snake_case`；除场地 `status` 可省略且默认为 `OPEN` 外，输入字段均必填。列表接口返回 JSON 数组，无分页；场地按 `id` 升序，预约按 `id` 降序。

| 方法与路径 | 用途 | 请求 | 成功响应 |
|---|---|---|---|
| `GET /api/venues` | 查询场地列表 | 无 | `200`，场地对象数组 |
| `GET /api/venues/{id}` | 查询场地详情 | 无 | `200`，场地对象 |
| `POST /api/venues` | 创建场地 | 场地输入对象 | `201`，创建后的场地对象，`Location` 指向详情 |
| `GET /api/reservations` | 查询预约列表 | 无 | `200`，预约对象数组，含已取消记录 |
| `GET /api/reservations/{id}` | 查询预约详情 | 无 | `200`，预约对象 |
| `POST /api/reservations` | 创建预约 | 预约输入对象 | `201`，创建后的预约对象，`Location` 指向详情 |
| `POST /api/reservations/{id}/cancel` | 取消预约 | 无正文 | `200`，更新后的预约对象 |

取消接口采用任务书允许的显式 `POST .../cancel` 形式，返回 `CANCELLED` 状态。

### 3.1 字段与示例

创建场地请求：

```json
{
  "name": "羽毛球馆 A",
  "location": "体育中心 1 层",
  "capacity": 8,
  "open_time": "08:00",
  "close_time": "22:00",
  "status": "OPEN"
}
```

创建成功的场地对象包含以上字段和 `id`。`status` 只允许 `OPEN`、`CLOSED`。

创建预约请求：

```json
{
  "venue_id": 1,
  "booked_by": "软件技术小组",
  "reservation_date": "2026-10-30",
  "start_time": "10:00",
  "end_time": "11:00",
  "attendee_count": 3,
  "purpose": "小组活动"
}
```

创建成功的预约对象包含以上字段，以及 `id`、`status: "ACTIVE"`、`created_at`、`cancelled_at: null`。取消成功后同一对象的 `status` 为 `CANCELLED`，`cancelled_at` 非空。前端不得把客户端生成的状态或 ID 当作服务端事实。

### 3.2 错误响应与状态码

所有业务错误统一返回以下形状；`details` 只在字段校验失败时出现，不返回异常堆栈、SQL 或环境变量值。

```json
{
  "error": {
    "code": "TIME_CONFLICT",
    "message": "该场地在所选时段已被预约"
  }
}
```

| 情况 | HTTP | `error.code` |
|---|---:|---|
| JSON/必填字段/字段格式/过去日期或时间/时间顺序/开放时段/人数超出容量不合法 | `400` | `VALIDATION_ERROR` |
| 场地不存在 | `404` | `VENUE_NOT_FOUND` |
| 预约不存在 | `404` | `RESERVATION_NOT_FOUND` |
| 场地已停用 | `409` | `VENUE_CLOSED` |
| 同场地同时段已有有效预约 | `409` | `TIME_CONFLICT` |
| 未预期服务端故障 | `500` | `INTERNAL_ERROR` |

`400` 可以附 `details: [{"field":"start_time","reason":"必须早于 end_time"}]`。前端展示 `message`，并按状态码区分参数错误、资源不存在和冲突；后端记录内部错误日志，但不把内部细节发给用户。

## 4. 容器与配置契约

| 项目 | 约定 |
|---|---|
| `frontend/Dockerfile` | Node 阶段安装锁定依赖并构建；Nginx 阶段只复制静态产物与站点配置；使用 `.dockerignore`；监听容器内 `80` |
| Nginx | 浏览器请求相对路径 `/api/...`；代理到 `http://api:8080`，**保留 `/api` 前缀**；页面刷新由静态站点回退到 `index.html` |
| `api/Dockerfile` | Maven/JDK 阶段构建；JRE 阶段只带应用 jar 和运行依赖；使用 `.dockerignore`、前台 Java 主进程；监听容器内 `8080`；建议非 root 运行 |
| `database` | 使用 PostgreSQL 16 标准镜像；`postgres_data` 命名卷挂载到 `/var/lib/postgresql/data`；`pg_isready` healthcheck |
| 启动依赖 | `api` 等待 `database` healthcheck 通过；`frontend` 等待 `api` 的 `/actuator/health` 通过后启动，通过 Compose 网络访问 `api`；应用自身仍需正确处理运行时连接失败 |
| 宿主机端口 | `frontend` 映射 `${FRONTEND_PORT:-8080}:80`；`api`、`database` 默认不向宿主机发布端口 |
| API 健康端点 | `/actuator/health`；至少能反映应用及数据库连接状态，验收时从 Compose 网络或容器内访问 |

项目根目录提交 `.env.example`，并在 `.gitignore` 中忽略真实 `.env`。Compose 在项目根目录读取 `.env` 用于变量替换，且将变量显式传给相应容器；不能把“Compose 读取 `.env`”误当成“容器自动得到所有变量”。变量名固定如下：

| 环境变量 | 用途 | 提供给 |
|---|---|---|
| `POSTGRES_DB` | 数据库名 | `database`；拼接 API JDBC URL |
| `POSTGRES_USER` | 数据库用户名 | `database`；API 数据源用户名 |
| `POSTGRES_PASSWORD` | 数据库密码 | `database`；API 数据源密码 |
| `FRONTEND_PORT` | 前端宿主机端口，默认 `8080` | Compose 端口映射 |

API 的 JDBC URL 由 Compose 生成 `jdbc:postgresql://database:5432/${POSTGRES_DB}`，通过 `SPRING_DATASOURCE_URL` 注入；用户名与密码通过 `SPRING_DATASOURCE_USERNAME`、`SPRING_DATASOURCE_PASSWORD` 注入。仓库中不得提交真实密码、Token 或密钥，不得把密码写进 Dockerfile 或镜像。

`docker compose down` 不删除 volume；持久化验收不得使用 `-v`。Dockerfile 必须能从仓库源码独立构建，不依赖本机编译产物或缓存。镜像名称和标签应可辨识，不要求推送到公共镜像仓库。

### 4.1 应用与构建接入

- 加入 PostgreSQL JDBC 驱动和 Flyway；根据最终选定的 Spring Boot/Flyway 版本确认是否需要独立的 PostgreSQL 支持模块。
- Flyway 启用，迁移位置为默认的 `classpath:db/migration`；迁移打包进 API 应用，由 API 启动时执行。
- 设置 `spring.jpa.hibernate.ddl-auto=validate`。不使用 `create`、`update` 或其他初始化 SQL 机制重复建表，不将 Flyway SQL 挂载到数据库的 `/docker-entrypoint-initdb.d/`。
- 读取 `SPRING_DATASOURCE_URL`、`SPRING_DATASOURCE_USERNAME`、`SPRING_DATASOURCE_PASSWORD`；不在应用中写死账号、密码或 `localhost` 数据库地址。
- 容器内监听 `8080`；提供 `/actuator/health` 并反映数据库连接状态。
- 后端 Dockerfile 从 `api/` 源码独立构建。C 不预先创建 Maven 或 Spring 配置文件，以免覆盖 B 的实现。

Compose 的前后端构建上下文分别为 `./frontend` 和 `./api`，各使用对应 Dockerfile；构建后的镜像分别标记为 `venue-booking-frontend:lab1` 和 `venue-booking-api:lab1`。数据库固定使用官方镜像 `postgres:16.15-bookworm`，标签依据[官方镜像标签列表](https://hub.docker.com/_/postgres)选定。前后端镜像已从源码构建，三服务通信、业务读写与容器重建后的数据保留均已实测；详见[验收清单](acceptance.md)。`.env.example` 仅提供说明与示例占位值。

Compose 对三个数据库变量使用 `${VARIABLE:?message}`，变量缺失或为空时直接报告配置错误。数据库健康检查通过容器内 TCP 访问 `127.0.0.1:5432`，使用 `$$POSTGRES_USER` 和 `$$POSTGRES_DB` 保留变量到容器内展开；配置每 5 秒检查一次，超时 5 秒，启动宽限 10 秒，最多重试 12 次。`pg_isready` 用于检查数据库接受连接的状态，不代替 API 的凭据与数据库读写验证。
