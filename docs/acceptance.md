# Lab 1 验收与报告清单

依据：课程提供的《云原生软件技术-Lab1-场地预约系统开发与Docker容器化.pdf》（仅本地参考，不纳入 Git）。以下是最终提交前的检查项；尚未执行的项目不得在报告中写成已通过。实际接口与配置以[公共契约](contract.md)及最终代码为准。

当前仅实现前端；本地安装、自动检查和模拟 API 手动操作见[README](../README.md)。模拟 API 的结果不计入真实后端、数据库或 Compose 验收。

## 1. 功能与错误

| 检查 | 合格结果 |
|---|---|
| 场地 API | 创建、列表、详情均可用，数据真实写入数据库；前端展示列表和详情 |
| 预约基本流程 | 前端创建预约、显示成功信息、查看预约列表和详情、取消预约 |
| 冲突与释放 | 同场地同日期时段重叠返回 `409`；相邻时段可预约；取消后原时段可重新预约，旧记录仍显示 `CANCELLED` |
| 输入和不存在资源 | 必填字段、日期/时间、开放时段、人数、停用场地得到明确错误；不存在 ID 返回 `404`；无异常堆栈暴露 |
| 并发冲突 | 同场地同日期同时段并发提交两次，只有一条有效预约成功，另一条返回 `409` |

## 2. 容器、数据与可复现性

从仓库源码复现并记录命令结果：

```text
复制 .env.example 为 .env，填入仅供本地实验使用的配置
docker compose up --build -d
docker compose ps
docker compose logs --tail=100
```

检查 `frontend`、`api`、`database` 三个服务正常；前端能访问 API，API 能通过 `database:5432` 访问 PostgreSQL，数据库 healthcheck 正常，日志中没有持续重复的严重错误；只有确需从宿主机访问的端口被发布。前后端镜像必须能由各自 Dockerfile 从源码构建，镜像中不包含真实密钥。

持久化验证须记录预约 ID，按下列顺序操作，并在重新启动后查询同一 ID：

```text
docker compose down
docker compose up -d
docker volume ls
```

预约仍存在、项目数据库 volume 可见才算通过。`down` 不加 `-v`。仓库应有 `.env.example`；真实 `.env` 必须被 `.gitignore` 忽略，不提交真实账号、密码、Token 或密钥。启动命令、访问地址和环境变量应写入 README，让其他人能够从干净环境复现。

## 3. 实验报告与提交

报告只记最终代码中实际存在的接口、配置和验证结果，至少包含：

| 内容 | 应记录的材料 |
|---|---|
| 系统架构、数据库结构、API | 三组件通信图；表主外键与取消方式；实际接口、字段、成功与错误状态码 |
| 两个 Dockerfile 与 Compose | 构建/运行阶段、端口、网络、环境变量、数据库 healthcheck、named volume 的配置说明 |
| 部署与运行 | `up --build -d`、`ps`、关键日志和访问结果 |
| 主要业务用例 | 场地查询、正常预约、预约列表/详情、冲突被拒绝、取消、取消后同时间重新预约的操作及结果 |
| 数据持久化 | 创建预约 → `down` → `up -d` → 原预约仍存在 → `docker volume ls` 的完整记录 |
| 小组分工 | A、B、C 实际完成的文件、功能和验收工作；问题与解决过程可选，但只能写真实经历 |
